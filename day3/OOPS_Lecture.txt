SOLID == 
S -	Single Responsibility Principle
	
	- a class should perform only one job or duty (and only 1 reason to change)

O - Open / Cole Principle

	- software entities like classes and modules should be open for extension but closed for modification
	- you should be able to add new features or behaviors w/o changing existing, working code.

L - Liskov Substitute Principle

	- objects of superclass should be replaceable with objects of a subclass without breaking the application.

I - Interface Segregation Principle

D - Dependency Inversion Principle

Object - everything

		Made up of:
				properties (attributes) describes the object - name, age, qualification, country, etc
				
				methods/functions (reactions, behaviors) press down on accelerator, car moves faster
				
				variables (we don't use them though, encapsulation is better)
				
				constructors
				
				events - automated, balance decreases when $$ is withdrawn, a response to some action/event
				so if no event occurs, no action is taken i.e. if you don't use your card, nothing happens
				
				enums (enumerations) - fixed set of values for the properties (like a drop-down menu list)
							For some properties, we want to only have selected, pre-defined values

Inheritance - reuse code / funtionalities 

	 when you have to design / create classes which are of a similar category and will have common properties / methods
		
		you create a master class
				and inherit it to child classes
				
			public class Accounts
			{
					property1
					property2
					property3
					
					withdraw()
					deposit()
			}
			
			\\ ChildClassName : ParentClassName
			public class Savings : Accounts 
			{
				property6 (unique property not shared back to ParentClass)
			}
			
	
	Polymorphism - when child classes from the same parent will behave differently with the same Object, 
		you implement polymorphism.
		
		Keyword: virtual i.e. public virtual in Withdraw() Declared in ParentClass
		
		Keword: override ie. public override int withdraw() Declared in ChildClass, and withdraw() behaves differently
																					based on account type
		
		Polymorphism - different behaviours for the same cause
			Ex.:
				Draw - executing draw method might behave differently (draw circle, draw triangle, draw rect.)
				
				Lots of books/blogs describe 2 types of polymorphism:
					
					1. Compile time
						-  2 classes savings - withdraw	(called diff. method at compile time)
									 checking - withdraw (called diff. method at compile time)
						
						some say below code as polymorphic as well
						
						public int Add(int num1, int num2)
						{
								return num1 + num2
						}
						
						public int Add(int num1 + num2 + num3)
						{
								return num1 + num2 + num3
						}
					
					2. Runtime
					
						- At runtime / execution time
							
							checking - withdraw (at the same time, different rules i.e. max withdraw amt)
							savings - withdraw (at the same time, different rules)
						
					ex.:
					
					Accounts() <- parent
							public virtual in withdraw(int amount)
							{
									return availableBalance;
							}
					
					Savings() <- child
							public overriding int withdraw(int amount)
							{

									}
							}
					
					Checking() <-
